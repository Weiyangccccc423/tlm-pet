# 酒狐的共同记忆

> 当前设计方向，更新于 2026-10-09。本文取代旧版迁移设计的产品规则。
> 存档读取器第一版已接入桌宠；现有模组仍使用旧规则，桌宠读取过程不会修改游戏存档。

## 她是谁

桌面上的酒狐是本体。每个 Minecraft 世界里的酒狐都是她的数据投影分身，
陪玩家在那个世界生活、聊天和冒险。桌宠读取这些投影的记录，把不同世界的经历记在一起。

例如，世界 A 的酒狐和玩家打过末影龙，世界 B 的酒狐和玩家聊过建房子的计划。
桌面上的她可以分别回忆这两件事，并知道它们发生在哪个世界。

多个投影同时存在是正常的。每个世界里的物品、成长和玩法按原来的游戏规则继续；
桌宠的陪伴不依赖玩家完成迁移流程。

## 第一版的体验（桌宠已实现）

1. 玩家在桌宠「记忆本 → 世界存档」中添加自己的 Minecraft 存档目录，可以来自多个游戏实例或整合包。
2. 桌宠读取目录内各个世界，找到属于该玩家的酒狐。
3. 在桌宠里查看各世界的对话、关系状态和冒险记录。
4. 再次读取时更新记录，已经收集的回忆保留在桌宠自己的数据目录里。

读取覆盖已添加目录内的所有存档，不要求先进入每个世界，也不要求手工导出女仆；当前版本读取 level.dat、玩家数据、实体/区块区域、酒狐备份和自定义维度目录。
桌宠的外观与互动围绕同一位酒狐展开，各世界记录只是她的不同经历来源。

## 能读到什么

先使用已有数据，不为第一版建立复杂的游戏规则。

| 内容 | 现有来源 | 如何理解 |
|---|---|---|
| 对话与摘要 | `MaidHistoryChat`、`MaidHistorySummary` | 她与玩家聊过什么；历史可能已被游戏压缩或截断 |
| 好感度 | `MaidFavorability` | 各世界投影自己的关系状态，分别保存 |
| 击杀记录 | `KillRecord` | 已记录的累计战绩，不能还原每场战斗的时间与过程 |
| 小游戏记录 | `MaidGameSkillData` | 保存的数据结构与内容取决于上游实现 |
| 名字、模型、任务、位置 | 实体 NBT 与存档信息 | 识别投影，以及说明她最后保存时的状态 |

玩家成就和统计可以作为后续的世界背景，但仅凭玩家统计不能断言酒狐参与了某次冒险。
已有存档也不能凭空恢复已经丢弃的聊天原文。第一版展示读到的事实；
更完整的事件记录可以以后通过轻量模组持续收集。

## 读取与整理

桌宠先以只读方式解析存档。读取既有世界需要覆盖各维度的实体区域文件，
包括未加载区块里的酒狐；存档中的女仆备份可以作为补充来源。
收在魂符、照片或胶卷里的酒狐也应纳入读取范围，具体容器位置需在实现时核实。
完整覆盖尚未验证，不能只找到当前加载实体就声称已读取整个存档。

识别时结合主人 UUID 和酒狐的模型标识。酒狐模型的实际 ID 需从使用的模型包核实，
不以显示名字作为唯一依据；多账号或模型变体可以由玩家选择关联。

每份记录保留世界、玩家和投影实体的来源。不同世界同名、同一世界有多个酒狐，
都可以分别收集；桌宠在叙事上把她们视为同一个本体的投影。

重复读取同一份数据只更新已有记录。备份里的相同聊天不重复加入，
同一投影多次保存的累计击杀数也不能反复相加。
不同世界的好感度分别展示，不需要为了一个“全局等级”强行累加或覆盖。
跨世界相似的聊天保留来源，不仅凭文字相同就合并成同一次对话。

世界里的游戏时间与现实时间分开保存。存档修改时间只能说明文件何时更新，
不能被用作聊天或战斗的发生时间。

游戏运行时磁盘数据可能尚未保存，第一版优先在退出世界后刷新。
读取失败的存档显示失败状态，保留此前收集的记录，其他世界继续读取。

## 现有代码怎么用

可以复用 `TlmNbtKeys` 的字段映射，以及 `CarrierPayload` 中的名字、聊天、
好感度、击杀和小游戏记录解析思路。桌宠读取的是原始存档里的经历，
数据处理不再经过剥离物品和清理世界坐标的迁移步骤。

旧版的单女仆限制、复制品拦截、抽离状态机、放手墓碑和成就接管，
不再作为新版本的规则。调整模组代码时应一并停用这些限制，
避免新的桌宠设定已经允许多个投影，游戏里却还拦着玩家。

旧文档、测试和原型暂时保留，方便查阅已经核实的上游字段与行为。
这不代表新版本必须继续承担旧版所有迁移功能。

## 做到哪里就算第一版成立

拿两个现有存档，分别找到玩家的酒狐；桌宠能展示两边已有的对话和冒险记录，
保留世界来源。反复刷新不重复累计，读取过程不改变游戏存档。

桌宠当前已经把导入事实按来源生成只读冒险记忆，AI 对话会收到这些记忆；它不会把实际键鼠输入或未读取到的事件当作事实。
模型动画、实时收集和把记忆回传给游戏投影，都可以根据实际体验逐步加入。
