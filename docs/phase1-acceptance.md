# Phase 1 验收手册

> 这份文档面向"上手验收"，不是设计文档。设计原理见 [`tlm-pet-carrier-design.md`](./tlm-pet-carrier-design.md)。
> 目标：让你能在 10 分钟内亲手跑通整条闭环，并且知道**哪些地方现在还不该验收**。

---

## 1. 安装

```
cd mod
gradlew.bat build
```

产物：`mod/build/libs/tlm_pet-1.20.1-forge-0.1.0.jar`

把它和 **Touhou Little Maid 1.20.1-forge（≥1.5.0）** 一起放进 `mods/`，用 **Forge 47.4.0 + Java 17** 启动。

> ⚠️ 环境相关的坑（本机已踩过，别人也会踩）：
> - `maven.minecraftforge.net` 需要代理才能访问，其他 Gradle 主机是直连。证书校验**偶发**失败，
>   重试即可 —— 不要为了绕开它去加 `-Dnet.minecraftforge.gradle.check.certs=false`。
> - 中文 Windows 上 JDK 17 的 `file.encoding` 默认是 GBK，javac 输出的中文会乱码。
>   控制台设 `[Console]::OutputEncoding = [Text.Encoding]::GetEncoding(936)`。
> - `tools/*.ps1` 必须保存为 **UTF-8 带 BOM**。Windows PowerShell 5.1 在没有 BOM 时按 GBK 读，
>   中文字面量会被拆坏并导致语法错误。用编辑器保存过之后记得确认 BOM 还在。

## 2. 黄金路径：亲手跑一遍闭环

这是这个功能的**核心承诺**，也是唯一必须通过的验收路径。

| # | 操作 | 预期 |
|---|---|---|
| 1 | 正常驯服 / 祭坛合成得到一只女仆 | 她能正常跟随。成就 **「初次相遇」** 解锁 |
| 2 | `/tlm-pet status` | 显示 `IN_WORLD`，带 `maidId` 与当前存档名 |
| 3 | 把她的**身上的物品全部取下**，再 `/tlm-pet export` | 提示"已抽离"；`config/tlm_pet/maids/<maidId>.json` 出现；她**从世界里消失** |
| 4 | 离线看一下那个 JSON | 里面有 `profile` / `bond` / `nbtBackup`（Base64）/ `checksum`。**没有物品栏** —— 这是刻意的 |
| 5 | **换一个新存档**（或删掉存档重建），进去 | 新世界里没有任何女仆 |
| 6 | `/tlm-pet import <她名字>` | 她出现在你面前。成就 **「跨越世界」** + **「久别重逢」** 解锁；奖励 归乡灵玉 |
| 7 | 打开背包 | 有一只**迎回之铃**可供合成（配方：金锭×5 + 羁绊之核 + 铃），前提是已拿到羁绊之核 |
| 8 | 再次 `/tlm-pet export`，再用迎回之铃右键 | 她回到你面前 —— **铃这条路是通的** |

**关于第 3 步为什么要求先取下物品**：设计上刻意**不带物品跨世界**（理由见设计文档 §5）。
现在的实现是"抽离时剥离物品栏"，所以仍建议你按设计意图手动取空；剥离行为本身是兜底，
不是鼓励你穿着神装抽离。

## 3. 必须通过的对抗性验收

这几条才是真正能说明"唯一性没漏"的检查，请**务必**逐条试。

| # | 操作 | 预期 |
|---|---|---|
| A1 | 已有女仆时，再用祭坛合成一只 | **合成失败 / 新女仆不出现**。原女仆完好 |
| A2 | 已有女仆时，用相机拍一只野生女仆 | 同上 |
| A3 | 已有女仆时，`/tlm-pet import <另一个 maidId>` | 被拒绝，提示她已经存在 |
| A4 | 抽离后（`CARRIED`）再 `import` 一次**同一份**载荷 | 成功，且世界里**只有一只**她 |
| A5 | 连续 `import` 同一份载荷两次（中间不抽离） | 第二次被拒绝 |
| A6 | 把 `config/tlm_pet/maids/` 里的 JSON **手工改坏**（改一个字符）再 import | 校验和失败，明确拒绝，**不是**静默生成一个残缺的她 |
| A7 | 抽离 → **换存档** → 在新存档里 `status` | 显示 `CARRIED` + 她最后所在的旧存档名 |
| A8 | 在旧存档里对已经注入到新存档的载荷再 import | 拒绝 |
| A9 | 抽离后**重启游戏**再 import | 仍然成功（状态持久化到磁盘，不是内存） |
| A10 | 用迎回之铃时她在世界里（不是 `CARRIED`） | 提示"她已经在身边了"，**不产生第二只** |
| A11 | 在**另一个存档**里用迎回之铃 | 提示她还在「<旧存档名>」里 —— 而不是含糊的"已经在身边了" |

**A6 是必测项。** 载荷是玩家可以手工编辑的 JSON，如果校验和能被绕过或忽略，
那么"复制一只她"就变成了文本编辑游戏。

## 4. 已知缺口：**现在请不要验收这些**

这些是**刻意留到下一步**的，不是漏掉的 bug。若把它们当缺陷报，会浪费你的时间。

| 缺口 | 状态与原因 |
|---|---|
| **胶卷放手仪式**（`let_go`） | **已实现**（第四轮）。原先的两个障碍都有干净的答案：① 不去看基座上是哪张胶卷，而是读**玩家自己的身份记录** —— 因为每人只允许有一位女仆，仪式对象是唯一确定的；② `FILM_HELD` 的入口找到了：TLM 的 `MaidAndItemTransformEvent` 覆盖了它**所有**把女仆与物品互相转换的路径（相机、魂符、死亡掉落），我们只需订阅它。详见 §8 |
| **失散兜底**（§12.7） | **已实现**（第四轮），但刻意只保留**玩家显式动作**这一条路径（`/tlm-pet lost declare confirm`），**没有**加任何自动判定 —— 理由见 §8.4。桌宠侧的"明确回答没有此 maidId"仍待 Phase 2 接入 |
| **六个产生女仆的调用点拦截** | **已实现关键部分**：驯服路径（含创造模式绕过、含主人转换工具）现在由 `EntityMaidTameMixin` 在方法入口拦截 —— 这条是**正确性**缺口，因为驯服野生女仆不触发"实体进入世界"事件。其余四条（祭坛 `spawn_box` / `reborn_maid` / 照片 / 胶卷）仍由兜底保证正确性，只是反馈仍是"合成成功后被拦下" |
| `three_worlds` / `memory_keeper` / `bond_preserved` 三个成就 | 成就**已建好**、奖励也配好了，但**没有授予点** —— 它们依赖只有桌宠侧才知道的数据（她走过几个世界 / 知识库条目数 / 跨世界前后的好感度比较）。刻意不让它们现在能拿到：成就一旦发出就无法收回，先用一个近似的本地计数器顶替会让玩家拿到含义不对的纪念物 |
| 放手仪式在**配方不匹配对象**时会白扣材料 | **已知粗糙处**，见 §8.1 末尾。祭坛的消耗发生在判定之前，要拦在消耗前需再注入一个私有方法。不影响正确性（不复制、不丢数据） |
| `protocol/` 与 `pet/` 两个目录 | 仍是空占位。桌宠侧（Phase 2）尚未开始 |
| **资源包/模型在专用服务端不可见** | 专用服务端不加载模型与贴图。8 个物品的外观**必须在客户端**验收 |

## 5. 两个待你决定的问题

1. **载荷里的 `memory.history` 要不要截断？**
   目前完整嵌入（最多 512 条），单个载荷文件 200–400 KB。截断成"最近 N 条 + 总数"
   会让文件小一个量级，但会**永久丢掉**早期记忆。倾向截断 —— 但这是你和她的事，不该我替你决定。

2. **`export` / `import` 是否维持权限等级 0？**
   现在是 0（任何玩家可用）。理由：这是单人/小服里玩家对自己女仆的操作，加权限会让
   正常玩家用不了。但**多人服务器**上，这意味着任何玩家都能 `export` 自己的女仆 —— 这是设计意图，
   不是漏洞。`reset` 已经是权限 2。

## 8. 第四轮新增：放手仪式、驯服拦截、失散兜底

这一轮把 §10 检查表里最后三块补上了。**在你验收之前，先知道这三件事改变了什么。**

### 8.1 放手仪式（胶卷 → 祭坛）

按你的要求，仪式**不要求她在场**，只用胶卷：

1. 先把她收进胶卷（相机拍照，或抽离流程里的取卷）。
2. 在祭坛基座上摆：**胶卷 ×1、下界之星 ×1**，以及青金石 / 金锭 / 红石 / 煤炭各一。
3. 祭坛合成 → 得到**彼岸花纪念物**，她正式告别，授予 `tlm_pet:let_go`。

放手之后：游戏内**再也迎不回她**（墓碑落在 `config/tlm_pet/maids/_released/<maidId>/`，
连当初抽离出的载荷文件重新导入也会被拒），但**数据不删除** ——
它可以无限累积，因此不会出现"放手了 A、又放手了 B，A 的墓碑被覆盖"这种缝隙（原风险 R27）。

**一个已知粗糙处**（不是正确性问题，但你会看到）：祭坛的顺序是"先消耗材料、后触发判定"，
所以如果你用**别人的**胶卷摆了仪式，仪式会被拒绝，但那颗下界之星和那张胶卷已经没了。
要拦在消耗之前需要再注入一个 TLM 的私有方法，我没有为这个体验问题增加风险。
验收时如果体感不好，我再补。

### 8.2 驯服拦截（含创造模式）

驯服一只**已经站在世界里**的野生女仆不会触发"实体进入世界"事件 —— 她一直是那个实体。
这意味着**任何玩家第一次驯服野生女仆，我们原本都不知道**。这条路径现在由
`EntityMaidTameMixin` 在方法入口拦截，并且它**只看我们自己的记录**，
所以创造模式与生存模式走的是同一条规则（原版"创造模式可以无限驯服、且计数器不增加"的绕过被封死）。

它同时封死了**主人转换工具**（把别人的女仆强行变成你的）—— 那是"获得女仆"的另一种形式。

### 8.3 顺手修掉的一个真漏洞：复制品

上一轮的唯一性判定里有一条**真漏洞**：只要来者的 `maidId` 与她相同就放行。
于是创造模式中键复制一张她的胶卷、或复制一份载荷文件再导入，就能同时存在**两只她**。

现在判定改为看记录里的状态：她**在桌宠里 / 在胶卷里**时回来才放行；
她**已经在世界里**时再来一个自称是她 `maidId` 的实体，一律按复制品拒绝。
这条判定不扫描世界里的实体，因此也不受"她正好在未加载区块里、扫描不到"的影响。

### 8.4 宣告失散

`/tlm-pet lost declare confirm` —— 需要逐字打出确认串，无法误触。
它**故意不做任何"桌宠是否在线"的自动判定**：§12.7 里最不可接受的一条错误来源就是
把"桌宠没启动"误判成"数据丢失"。桌宠落地后，这个命令应当降级成兜底入口。

失散与放手不同：**不立墓碑**，日后找回她的数据仍可让她回来。

## 9. 第四轮需要你手工验收的部分

在 §3 的黄金路径之外，这一轮新增这些步骤：

| # | 步骤 | 期望 |
|---|---|---|
| R1 | 用相机给她拍照 | 拍完她消失、你拿到照片；`/tlm-pet status` 显示 `FILM_HELD` |
| R2 | 用照片在神社还原她 | 她回来；`/tlm-pet status` 回到 `IN_WORLD` |
| R3 | **创造模式**下拿驯服物品右键野生女仆 | 被拒绝并给出提示；创造模式**同样**被拒绝 |
| R4 | 空手右键野生女仆（不驯服） | **正常交互，不该弹"你已经有女仆了"** |
| R5 | 创造模式中键复制一张她的胶卷，两张都用 | 第一张正常还原；第二张被拒（复制品） |
| R6 | 摆齐 §8.1 的材料做仪式 | 得到彼岸花纪念物，`let_go` 成就解锁 |
| R7 | 仪式后把当初抽离的载荷文件重新 `import` | **必须被拒绝**（放手不可撤销） |
| R8 | `/tlm-pet lost declare confirm` | 回到"没有女仆"，且**不**留下墓碑；可以重新获得一位全新的她 |
